# Project: Distributed MCP Gateway Architecture (King-Worker Pattern in Go)

## Architecture
The `dca` application is enhanced with a distributed King-Worker architecture enabling secure MCP tool invocation across NATs and firewalls via WebSocket reverse tunneling, session resumption, and protocol inversion.

- **Worker Daemon (`dca worker`)**: Runs on child devices. Generates 6-character pairing codes when un-paired. Initiates persistent outbound WebSocket connections (`wss://<king>/register`) with `X-Node-ID` and `Authorization` headers. Tool executions occur in isolated goroutines; completed JSON-RPC responses are buffered in an `Outbox` queue and flushed over WebSocket. If connection drops mid-execution, items remain queued and flush upon reconnection.
- **King Control Plane (`dca king`)**: Acts as central gateway. Manages device pairing via `dca king add-device <code>`, issuing single-use encrypted pair tokens. Accepts incoming worker WSS registrations at `/register`, maintains active tunnels in `ActiveConns` (`sync.Map`), and functions as MCP Client. Provides URL route-based MCP ingress at `/<device_id>/mcp`, forwarding calls down the worker tunnel. Manages a transport-agnostic `PendingRequests` map with UUID request ID rewriting and 30-second session recovery windows.
- **CLI & Config Integration**: Integrates commands (`dca king`, `dca worker`, `dca pair`) into `main.go` and extends `ServerConfig` while ensuring full backward compatibility for standalone, service, and TUI modes.

## Interface Contracts

### Worker ↔ King WebSocket Protocol
- **Endpoint**: `wss://<king_host>:<port>/register`
- **Headers**:
  - `X-Node-ID`: Unique ID of the worker node.
  - `Authorization`: Bearer token (single-use pair token issued by King).
- **Frames**: JSON-RPC 2.0 frames forwarded bi-directionally over text WebSocket frames.

### King Single-Use Pairing Exchange
- **Command**: `dca king add-device <code>`
- **Logic**: Validates 6-character temporary code generated by worker, generates an encrypted JWT / pair token, marks code as consumed. Subsequent validation attempts with the same code return error.

### King Ingress & Pending Map Contract
- **Ingress URL**: `POST /<device_id>/mcp`
- **Body**: JSON-RPC 2.0 payload (e.g. `tools/call`, `tools/list`, `initialize`).
- **ID Rewriting**: Incoming request `id` (e.g., integer or string) is rewritten to a fresh UUID before tunneling to the worker.
- **Pending Map**: Maps rewritten UUID -> response channel with a timeout (e.g., 30s). Disconnections during handling keep the channel waiting until reconnect/flush or timeout.

## Code Layout
- `utils/server_config.go` — Extended `ServerConfig` struct with King/Worker parameters.
- `utils/outbox.go` — Thread-safe `Outbox` queue for session resumption.
- `utils/worker_daemon.go` — Worker daemon, pairing code generator, WSS reverse tunnel client.
- `utils/pairing.go` — Single-use pairing code and token management.
- `utils/king_gateway.go` — King gateway control plane, `/register` WSS listener, `ActiveConns` map.
- `utils/king_ingress.go` — `/<device_id>/mcp` HTTP ingress handler, `PendingRequests` map, UUID ID rewriting.
- `main.go` — CLI subcommand routing (`king`, `worker`, `pair`, `run`, `start`, `stop`, etc.).
- Unit test files corresponding to each package in `utils/`.
- E2E test files in `tests/e2e/`.
